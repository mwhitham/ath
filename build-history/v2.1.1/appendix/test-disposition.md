# Existing test disposition (reference commit c6218e88)

This table maps every `tests/*.test.ts` file at commit
`c6218e88c035708bdd15b3a20888d19713e1df29` to the promises it checks and to the place
that will check them after the rebuild (spec section 13.3). The number of tests is not a
quality claim. What matters is which promises each file checks and which promises no
file checks.

The Kind column uses three values:

- `public behavior`: the promise can be observed by an athlete, an agent using the CLI,
  a direct-SQL reader, a JavaScript caller of the published exports, or a file-format
  consumer, and the code under test still runs in the product. Some of these files reach
  the promise through an internal TypeScript helper or a test-only hook. The cell says so,
  because the port must use a public or native entry point instead.
- `retired internal machinery`: the file tests TypeScript code that the rebuild removes,
  or code that no longer runs in the product at this commit.
- `mixed`: the file does both. The cell names the parts.

The Planned home column names where the promise is checked after the rebuild. A file can
have more than one home. Fixtures are listed under "Fixtures and helpers".

## Coverage gaps and uncertainty

### Uncertain classifications

1. Spec section 10 says to port ECG peak detection, beat intervals, RMSSD arithmetic,
   route splits, and elevation. Section 5 does not say whether they belong in `import`
   or `calculate`. The rows for `ecg`, `hrv`, and `routes` name both.
2. The allowed destination forms have no `tools/` entry. `v1-docs` (documentation
   consistency), the generated CLI reference check in `skill`, and the generator in
   `v1-performance-generator` would fit `tools/` better than the homes named here.
3. `v1-performance-generator` tests release tooling, not a product promise. Section 14
   needs the same deterministic datasets, so the generator is not simply retired.
   The old generator can keep running in the reference checkout for comparisons.
4. Several files reach a public promise only through a live internal helper or a
   test-only hook: `ecg`, `routes`, `progress`, `gateway`, `keyring`, `models`,
   `mapping-path`, `import-safety`, `update`, and `v1-export-staging`. They are marked
   public behavior. A stricter reading could mark them mixed.
5. `v1-route-table-guard` has the title "tells you to migrate", but it only checks
   that the message names the missing table. The replacement must decide whether a
   migrate hint is required.
6. `apple-rust-parity.json` could be kept as reference evidence or dropped. It does not
   describe a public format.
7. Version strings in `cli`, `v1-package-exports`, `skill`, and `version-2-1` expect
   2.1.0 and schema 4. Section 12 changes those for 2.1.1 and migration 005. Those
   expectations will change on purpose. They are not behavior regressions.

### Promises the existing tests check only against code that no longer runs

1. WHOOP offset spellings. `csv.test.ts` checks `src/import/csv.ts`, which nothing
   imports. The live parser is in `crates/ath-core/src/whoop.rs`. Its two Rust tests
   cover a fractional-second offset and one cycle. The UTC-prefixed, bare, and zero
   spellings are checked only indirectly by the WHOOP baseline row.
2. Apple beat clock placement. `apple.test.ts` has about ten `beatOffsetMs` cases on
   a TypeScript copy that no longer runs. The live Rust `beat_offset_ms` has one test.
3. RMSSD from Apple beats. `hrv.test.ts` checks the missed-beat, dropped-beat,
   continuous-pair, and 10-second-window rules on `rmssdFromBeats`, which no longer
   runs. One related Rust test exists (SDNN and RMSSD stay separate). This review did not
   check whether the Rust code applies the same rules.
4. Coverage windows chosen by instant rather than by day string. Only the retired
   `coverage.test.ts` checks this.

### Public promises with no test found

1. `ath key set`, `key clear`, and key status as commands. Only the helpers are tested.
2. `ath models` as a command (listing and saving a default). Only its help is checked.
3. `ath predict` with a model, and the rule that a network failure leaves no partial
   prediction.
4. `ath backtest` as a command, and partial model failures in a backtest report.
5. `ath pull garmin` failures (missing key, server error). Only the success path runs.
6. `ath export --exported-at`. Tests check only that the time is absent by default.
7. `conflicts resolve --choice local` and `--choice corrected`. Only `imported` is used.
8. `ath init` interactive profile prompts. Every test uses `-y`.
9. Standard input to `ath log`. The `v1-cli-writes` helper accepts input, but no call this review
   read passes any.
10. The `share` placeholder staying unimplemented. Only its help text is checked.
11. Remote libSQL targets: URL parsing, the operations that work, and the refusals.
    Spec section 11.2 asks for an inventory and preserved results.
12. Closed-handle behavior on a database handle.
13. Direct JavaScript use of most `athleticstandard/database` exports. For example,
    `planLogEntry`, `applyLogPlan`, `gradePrediction`, `planPredictionGrade`,
    `previewRecordErasure`, `eraseRecord`, `querySessions`, `readSeriesView`,
    `renderRecord`, `renderRecordList`, `buildEvidence`, the saved conflict-set
    functions, and the attachment helpers run only inside CLI tests. Section 11.2
    needs one compatibility test per exported symbol.
14. A full Garmin account export zip. The tests have single-activity files and a zip detection
    case, but no import of an account export.
15. Attachment file removal during `ath erase`. The erase test checks records and
    markers, not files. No test injects a failure into erasure or attachment import.
16. `ath calculate` as a command for operations other than `baseline`. The other
    operations run only through the library.

### Test conditions the replacement should change

1. Several cases run only off Windows: all of `v1-cli-sidecar` and
   `v1-wal-failed-write`, four `v1-db` cases, and three `v1-repair-cli` cases. Spec
   section 13.2 requires native CLI tests on Windows too.
2. Several tests need the external `sqlite3` program: `v1-sql-contract`,
   `v1-repair-cli`, `v1-wal-failed-write`, `version-2-1`, and the raw-hash helper.
   Spec section 7 allows an independent SQLite connection for direct-SQL checks.
   Native smoke tests must run without `sqlite3`.
3. The import baseline forces `TZ=UTC` for the mismatched-route row because one GPX
   point has no offset. Spec section 13.2 asks for that case without forcing the
   suite to UTC. The replacement should run it under more than one zone or assert the
   documented result directly.
