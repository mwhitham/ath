# v0.4.3 migration mapping

Status: review checkpoint. Runtime implementation does not begin until this appendix
is approved.

This appendix maps every field accepted by the v0.4.3 Zod schemas to the v1.0.0
logical records. It describes migration only. The v0.4.3 files and sidecars remain
unchanged.

## Migration transaction

`ath init` creates an empty v1.0.0 database with a new database ID. Importing a
v0.4.3 document then:

1. Runs `validateAthleticStandardFile` with the shipped v0.4.3 schema and semantic
   checks.
2. Reads and verifies every available series sidecar and attachment.
3. Builds the complete import preview only after those checks pass.
4. Resolves old source, benchmark, session, result, and prediction references.
5. Writes every accepted record in one transaction after confirmation.
6. Gives each imported record revision 1.
7. Increments the database revision once for the whole import.

The destination keeps the database ID created by `ath init` because a v0.4.3 file
has no database ID to adopt. A fixed import time may be supplied by tests and
reproducible tooling. Revision knowledge times follow the marked legacy rules below;
they are not all replaced with the import time.

The original document, `series/`, `attachments/`, model preference, backtest reports,
and installed Skill files are not modified.

## How to read a destination

Every destination in this appendix is an exact v1 record kind, SQLite table, or
SQLite column. Plain-language category names are not destinations.

Every athlete-owned record writes three common rows:

- `records` holds `id`, `kind`, `current_revision`, `created_at`, and deletion state.
- Its typed table holds the current fields. For example, an athlete report uses
  `soft_signals`.
- `record_revisions` holds revision 1 and the complete logical record state.

Every imported record also writes
`record_import_keys(record_id, key_recipe, import_key, source_format_version,
imported_at)`. `key_recipe` is `legacy-v0.4-id-v1`. `import_key` is the encoded
UUIDv5 name described below. `source_format_version` is copied from the top-level
`athleticstandard_version`. `imported_at` is the migration transaction time. Child
rows such as segments use their named child table and their parent's stable ID. The
field tables below do not repeat these common writes on every line.

For example, one old soreness item writes:

```text
records(kind = athlete_report)
soft_signals(record_id, report_type, reported_at, rating, rating_scale, body_region, text)
record_revisions(record_id, revision = 1, complete state)
```

It writes `attachments` only when the old item references one. It never writes a
source foreign key.

## Stable IDs

New v1 records use UUIDv7. Legacy records use UUIDv5 under a fixed Athletic Standard
namespace.

The legacy namespace UUID is `a4f17b95-1205-5b33-b97a-cb95098e9b12`. It is the
UUIDv5 result of the RFC namespace URL and
`https://athleticstandard.ai/namespaces/legacy-v0.4`.

The name begins with the string component
`athleticstandard-legacy-v0.4-id-v1`. Each following component is encoded in order.
A string is `s`, its UTF-8 byte length in ASCII decimal, `:`, then its unchanged
UTF-8 bytes. A nonnegative integer uses `i` followed by the same length form for its
ASCII decimal text. An absent optional value is `n0:`. There are no separators
between encoded components. UUID text used as a component is lowercase. This
encoding distinguishes absent, empty, string, and integer values and does not depend
on JSON key order.

The component lists are:

| Legacy record | UUIDv5 name input |
|---|---|
| Athlete profile | `athlete_profile` |
| Source | `source`, old source ID |
| Source device | `source_device`, source UUID, `name`, `manufacturer`, `model`, `hardware`; add original device position when those fields repeat |
| Point measurement | `point`, type, source UUID, `recorded_at`; add original position when repeated |
| Vendor score | `vendor_score`, metric, source UUID, `recorded_at`; add original position when repeated |
| Series receipt | `series_receipt`, quantity, source UUID |
| Series sample | `series_sample`, quantity, source UUID, reconstructed instant; add original sample position when repeated |
| Sleep session | `sleep_session`, source UUID, `start`; add original position when repeated |
| Workout session | `workout_session`, source UUID, `start`; add original position when repeated |
| Benchmark definition | `benchmark`, old benchmark ID |
| Benchmark result | `benchmark_result`, benchmark UUID, source UUID, `recorded_at`; add original position when repeated |
| Athlete report | `athlete_report`, type, `reported_at`; a later duplicate adds `note`, then original position if still repeated |
| Prediction | `prediction`, old prediction ID |
| Prediction outcome | `prediction_outcome`, prediction UUID, linked result UUID |
| Attachment | `attachment`, owning record UUID, old filename, expected SHA-256 |
| Grade | `grade`, prediction-outcome UUID, `legacy-v0.4-grade` |
| Miss analysis | `miss_analysis`, prediction UUID, `legacy-v0.4-miss-analysis` |

Mutable source-device coverage fields `from`, `to`, and `n` are not ID components.
Original position is zero-based in the v0.4.3 array. A series sample's position is
its zero-based global index after sorting sidecars by filename day and then walking
each file's parallel sample arrays in order.

The first occurrence of a base reference keeps the base UUID. Each later collision
adds its original position to the UUIDv5 input. This implements the plan's
deterministic-suffix rule. Repeating the same package produces the same IDs.

Migration also stores the encoded UUIDv5 name as a
`record_import_keys` entry with recipe `legacy-v0.4-id-v1`. On another import, the
same key and same complete migrated content is a match. The same key with changed
content is previewed as a correction and creates a revision only after confirmation.

Ordered segments, derivation details, prediction evidence details, and other child
rows are part of their parent record state. They use the parent ID and their
zero-based order. They do not receive independent legacy UUIDs. Correcting one
creates a revision of the parent and replaces its child rows in the same transaction.

## Top-level document

| v0.4.3 field | v1.0.0 destination | Rule |
|---|---|---|
| `athleticstandard_version` | `record_import_keys.source_format_version` on every imported record key | Must be a supported `0.x` version. The live database format remains `1.0.0`. |
| `athlete` | `records.kind = 'athlete_profile'`, `athlete_profile`, `record_revisions` | Mapped field by field below. |
| `sources[]` | `records.kind = 'source'`, `sources`, `source_devices`, `record_revisions` | Old IDs become legacy keys and are mapped to stable UUIDs. |
| `hard_signals[]` | `records`, `record_revisions`, and the exact `records.kind` and typed table in the dispatch table below | Array position is retained for diagnostics and collision handling. |
| `soft_signals[]` | `records.kind = 'athlete_report'`, `soft_signals`, `record_revisions` | No source column or source foreign key is added. |
| `benchmarks[]` | `records.kind = 'benchmark'`, `benchmarks`, `record_revisions` | Old benchmark IDs remain human-readable keys. |

Unknown top-level or nested fields cannot occur in a valid strict v0.4.3 document.
An input claiming a newer format is previewed with its unknown fields and is not
applied.

This mapping accepts a `0.x` version at or before 0.4.3 only when the complete
document passes the v0.4.3 schema and semantic checks. A retired layout that no
longer fits that schema follows the refusal rule in Dense series.

The `hard_signals[]` dispatch covers the complete v0.4.3 `HardSignal` union:
point measurements, sleep sessions, workout sessions, benchmark results,
`series_ref`, and `vendor_score`. Its array index is used for diagnostics and only
as the collision rule in the Stable IDs table. It is not the primary ID input.

## Shared time and source receipts

v0.4.3 stores normalized ISO timestamps, not the exact vendor timestamp text that
preceded parsing. Migration preserves the v0.4.3 timestamp and its printed numeric
offset in the exact typed-table columns below. It marks their meaning
`legacy_normalized_timestamp`. Migration does not call the offset a recording
timezone. No IANA timezone is inferred.

Original provider units and values were generally discarded after conversion in
v0.4.3. The normalized value and unit are preserved. Their original-source fields
use the absence reason `legacy_not_stored`.

Every migrated measured record sets `time_received` to the v1 migration transaction
time and `time_received_basis` to `legacy_migration_time`. This is when v1 received
the record, not when the old importer first saw the provider row.

The exact columns are `point_measurements.time_received` and
`point_measurements.time_received_basis`, `series_samples.time_received` and
`series_samples.time_received_basis`, `series_receipts.time_received` and
`series_receipts.time_received_basis`, `sleep_sessions.time_received` and
`sleep_sessions.time_received_basis`, `workout_sessions.time_received` and
`workout_sessions.time_received_basis`, `benchmark_results.time_received` and
`benchmark_results.time_received_basis`, and `provider_scores.time_received` and
`provider_scores.time_received_basis`.

The parent `records.created_at` copies the same instant as revision 1
`record_revisions.known_at`, listed below. Its basis lives in
`record_revisions.known_at_basis`; `records` does not duplicate that basis.
Predictions keep their old authored `created_at`. The actual v1 import time is stored
in `record_import_keys.imported_at`. No unmarked record-creation time is invented.

The exact time-receipt columns are:

| `records.kind` | Timestamp receipt columns |
|---|---|
| `point_measurement` | `point_measurements.source_timestamp_text`, `point_measurements.source_offset_text`, `point_measurements.source_time_basis` |
| `sleep_session` | `sleep_sessions.start_source_text`, `sleep_sessions.start_source_offset_text`, `sleep_sessions.start_source_time_basis`, `sleep_sessions.end_source_text`, `sleep_sessions.end_source_offset_text`, `sleep_sessions.end_source_time_basis` |

`series/` directory leaves that link pointed at the unavailable receipt. A missing
matching receipt is an import error.

### Sidecar files

The expected filename is
`series/<YYYY-MM-DD>-<quantity>-<source>.ath.series.json`. The leading date is the
sidecar day. Files are selected by the exact quantity and source suffix, as v0.4.3
did, because quantity underscores and source hyphens make delimiter splitting
ambiguous. Each selected file is parsed with the v0.4.3 `SeriesFile` schema before
any database write.

|---|---|---|

| `offsets_ms[i]` | `series_samples.recorded_at`, `series_samples.reconstruction_offset_ms` | Add the integer offset to `Date.parse(start)` in milliseconds. Preserve the offset as the reconstruction receipt. |
| `values[i]` | `series_samples.normalized_value`, `series_samples.original_value_absence_reason` | Preserve exactly. Set the absence reason to `legacy_sidecar_not_stored`. |
| `durations_ms[i]` | `series_samples.duration_ms` | Preserve when the parallel array exists. |

Each accepted sample writes `records.kind = 'series_sample'`,
`series_samples.record_id`, `series_samples.series_receipt_id`, and revision 1. The
receipt ID points to the `series_receipts` record for the same source and quantity.
Each sidecar writes one ordered child row in `series_sidecar_receipts` with
`series_receipt_id`, `ordinal`, `relative_path`, `source_format_version`,
`start_text`, and `file_sha256`. Each sample also sets
`series_samples.series_sidecar_ordinal` to that child row's ordinal.

| Sidecar child value | `series_sidecar_receipts` destination | Rule |
|---|---|---|
| parent series receipt UUID | `series_sidecar_receipts.series_receipt_id` | Link the `series_receipts` record for the same source and quantity. |
| filename-day order | `series_sidecar_receipts.ordinal` | Number from zero after sorting by filename day. |
| selected sidecar filename | `series_sidecar_receipts.relative_path` | Preserve the validated path relative to the package root. |
| `athleticstandard_version` | `series_sidecar_receipts.source_format_version` | Preserve the sidecar's version. |
| `start` | `series_sidecar_receipts.start_text` | Preserve the complete string verbatim, including its printed offset. |
| exact file bytes | `series_sidecar_receipts.file_sha256` | Store the verified lowercase SHA-256. |

Sidecar `quantity` and `unit` are not copied onto
`series_sidecar_receipts`. They are already preserved on the parent
`series_receipts.quantity`, `series_receipts.normalized_unit`, and every linked
sample.

Samples keep sidecar file order as their original position for collision handling.
The importer also verifies that offsets are nondecreasing, the filename day equals
the first ten characters of `start`, and sidecar quantity, canonical unit, and
source match the group.

The importer hashes each sidecar's exact bytes with SHA-256. It then rebuilds the
v0.4.3 group hash by adding
`<day>:<sidecar-sha256>\n` in filename-day order. That result must equal the
`series_ref.sha256`. It also verifies declared sample count, `from` and `to` against
the first and last filename dates, and `days` against the number of sidecars.
Samples are inserted in bounded prepared batches.

The quantity, source, unit, filename-day, offset-order, count, and coverage checks are
new migration integrity checks. v0.4.3 `ath check` rebuilt only the group hash after
schema validation. Migration makes these relationships explicit before moving the
samples into database rows.

The old sidecar did not keep each vendor timestamp text, original unit, or original
value. Each sample records the absence reason `legacy_sidecar_not_stored`. Its
reconstructed timestamp receipt names the sidecar start and offset.
The exact columns are `series_samples.original_timestamp_absence_reason`,
`series_samples.original_unit_absence_reason`, and
`series_samples.original_value_absence_reason`.

If the `series/` folder is absent, import writes one unavailable legacy series
receipt per source and quantity with the declared coverage and hash. It writes no
samples. `ath check` reports the missing sample data.

A present sidecar with a hash mismatch is not treated as absent. Import refuses
because the bytes disagree with the document's receipt.

If the `series/` folder exists but any declared sidecar is missing, malformed, or
fails the quantity, source, unit, count, coverage, or hash checks, import refuses and
writes no `series_receipts` or samples. It does not use a third availability value
for a partly present group.

### Inline and series copies

D43 moved dense quantities out of `hard_signals`. A legacy file may still contain an
inline point with the same quantity and source as a `series_ref`.

When verified sidecars are available, migration applies the v0.4.3 D43 rule: no
inline point with that quantity and source becomes a current point record. An exact
quantity, source, instant, value, and unit match is shown as an old duplicate in the
import preview. A nonmatching inline point is unrepresentable and blocks import.
It is neither silently dropped nor counted beside the dense series.

When the series folder is absent, inline points remain point records and the
unavailable series receipt remains. No sample is invented from an inline summary.

A document that claims v0.4.3 but carries retired per-day `series_ref` fields such
as `file`, `summary`, `start`, or `end` fails v0.4.3 validation. This appendix does
not guess how to upgrade a pre-D40 layout. The user must import the original provider
export or use a separately specified older-format upgrader.

A generic v0.4.3 `nutrition` report remains an athlete report with its original text,
rating, and attachment. Migration does not infer foods, amounts, or nutrients.

unrelated score field.

validation in migration step 1.

## Links

Before resolving links, migration checks for duplicate workout keys
`(source,start)` and duplicate result keys `(benchmark,recorded_at)`. General v0.4.3
validation collapsed those keys into a set or map and did not report duplicates.
Migration reports them as conflicts because a compound link cannot identify one
target.

### Result to workout session

The old `(source,start)` link resolves after all workout sessions have IDs.

- One exact match: write `benchmark_results.workout_session_id` and
  `benchmark_results.workout_session_revision = 1`.
- No exact match: import error.
- Several exact matches: conflict; do not choose by array order.

### Prediction to result

The old `(benchmark,actual.recorded_at)` reference resolves after all results have
IDs, using the rules above.

### Planned-session links

v0.4.3 has no training plans or planned sessions. Migration creates none.

## Revisions and tombstones

v0.4.3 has no revision or deletion records.

- Every imported current record begins at revision 1.
- Every revision stores the complete migrated logical record.
- `record_revisions.supersedes_revision` is null.
- `record_revisions.author_type` is `tool`.
- `record_revisions.author_tool` is `ath`.
- `record_revisions.author_tool_version` names the migration tool version.
- No tombstones are created from absence in the old arrays.

v0.4.3 did not record when a row first entered the file. Using the migration time
would hide the entire legacy history from an earlier `--as-of` query. Revision 1
therefore uses these marked assumptions:

| `records.kind` | `record_revisions.known_at` source | `record_revisions.known_at_basis` |
|---|---|---|
| `point_measurement` | `point_measurements.recorded_at` | `legacy_event_time_assumption` |
| `provider_score` | `provider_scores.recorded_at` | `legacy_event_time_assumption` |
| `benchmark_result` | `benchmark_results.recorded_at` | `legacy_event_time_assumption` |
| `series_sample` | `series_samples.recorded_at` | `legacy_event_time_assumption` |
| `sleep_session` | `sleep_sessions.end_at` | `legacy_session_end_assumption` |
| `workout_session` | `workout_sessions.start_at` | `legacy_session_start_assumption` |
| `athlete_report` | `soft_signals.reported_at` | `legacy_report_time_assumption` |
| `attachment` | owning `soft_signals.reported_at` | `legacy_report_time_assumption` |
| `prediction` | `predictions.authored_at` | `legacy_prediction_created_at` |
| `prediction_outcome` | linked `benchmark_results.recorded_at` | `legacy_result_time_assumption` |
| `prediction_grade` | its outcome's linked `benchmark_results.recorded_at` | `legacy_result_time_assumption` |
| `miss_analysis` | its grade's outcome-linked `benchmark_results.recorded_at` | `legacy_result_time_assumption` |

| `source_device` | parent source's earliest dependent `record_revisions.known_at` | `legacy_dependency_time_assumption` |
| `benchmark` | earliest dependent `benchmark_results.recorded_at` or `predictions.authored_at` | `legacy_dependency_time_assumption` |
| available `series_receipt` | latest linked `series_samples.recorded_at` | `legacy_dependency_time_assumption` |

These values preserve the historical visibility that v0.4.3 derived from event
times. They do not prove when the old file learned a fact. Historical query and
backtest receipts must state when an included revision uses a legacy assumption.

Running the same import against the same nonempty database finds matching IDs and
revision values. It creates no new revisions.

## Provider periods and local dates

The old logical document did not distinguish provider periods from calendar dates.
Migration preserves only what the document proves:

- Existing timestamp strings remain source timestamp receipts.
- Existing `SeriesRef.from` and `to` remain legacy coverage dates.
- Existing device `from` and `to` remain legacy device-window dates.
- No WHOOP cycle, Oura day kind, Apple activity-summary date, recording timezone, or
  travel history is inferred from a generic old timestamp.

Re-importing the original provider export under v1 may produce richer period
receipts. That is a separate provider import preview. It is not silently folded into
the migrated legacy record when the old file lacks a stable provider ID.

## Preview counts

Before confirmation, migration reports:

- Sources and devices.
- Current records by kind.
- Series receipts, available sidecars, accepted samples, and missing series groups.
- Attachments copied, missing, rejected, or hash-mismatched.
- Links resolved, missing, or conflicting.
- Legacy fields preserved with unavailable-original receipts.
- Unknown or unrepresentable records.

Any error, conflict, unknown field, missing required attachment, or unrepresentable
record prevents the transaction. A missing series folder is the one allowed partial
case because v0.4.3 explicitly permitted a document to travel without its series
sidecars. The unavailable series receipt makes that loss visible.

## Required migration fixtures

Migration tests include:

- Every point type, session aggregate, benchmark score type, and soft-signal field.
- Available series with millisecond offsets and durations.
- A missing series folder and its unavailable receipts.
- D43 inline points that both do and do not exactly match a sidecar sample.
- Vendor scores, derived-value receipts, and source-device windows.
- Result-to-session and prediction-to-result links.
- Attachments, including photo provenance and failed hash checks.
- Grades and miss analyses with hard-tier and soft-tier causes.
- An `actual` without a grade.
- A miss-analysis selector with several possible evidence records.
- Duplicate old references and repeat imports.
- A legacy Oura midnight UTC anchor.

## Round-trip acceptance

The migration is accepted only when:

1. Every v0.4.3 field above is present in the v1 logical export or in a named legacy
   receipt.
2. Every available series sample survives with its value, duration, quantity, source,
   and reconstructed instant.
3. Every old link resolves to stable record IDs without guessing.
4. The two-tier wall still holds.
5. Exporting and importing the migrated database produces equal logical records,
   revisions, tombstones, receipts, periods, and attachment hashes.
6. Repeating the v0.4.3 import produces no records or revisions.
