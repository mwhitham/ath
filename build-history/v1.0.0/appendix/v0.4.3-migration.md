# v0.4.3 migration mapping

Status: superseded by D101. This appendix is retained as a design record and will
not be implemented.

This appendix maps every field accepted by the v0.4.3 Zod schemas to the v1.0.0
logical records. It describes migration only. The v0.4.3 files and sidecars remain
unchanged.

## What migration changes

- **Live file.** Day-to-day work moves from `athlete.ath.json` and live `series/`
  files into `athlete.ath.sqlite`. JSON becomes a portable snapshot for explicit
  import and export. It does not stay synchronized with SQLite.
- **How to migrate.** Migration is never automatic. The intended commands are
  `ath init`, `ath import athlete.ath.json`, `ath check`, and optionally
  `ath export migrated-athlete/`.
- **Old files.** Import does not modify the old JSON, sidecars, attachments, model
  preference, or backtest reports. `ath init` may refresh the installed Skill as
  normal setup.
- **Preview.** Import validates the package and shows a complete preview. Unresolved
  conflicts, unknown fields, and records that cannot be represented stop the write.
  After confirmation, accepted records are written in one transaction. Any failure
  leaves the database unchanged.
- **IDs and history.** Every imported record gets a stable ID and revision 1.
  Repeating the same v0.4.3 package import into the same database creates no
  duplicates or extra revisions.
- **Sources.** Measurements keep their source. Athlete reports such as soreness,
  meals, and notes remain source-free. Hand-entered measurements remain marked as
  manual. Two old sources are never merged.
- **Dense samples.** Available sidecar samples move into SQLite. Counts, coverage,
  filenames, units, and hashes must agree. A completely missing `series/` folder is
  the only allowed partial case; migration records the gap and invents no samples. A
  partly present, damaged, or conflicting series set blocks import. When the folder
  is completely missing, any valid inline point measurements still import.
- **Times.** Migration keeps the timestamps and offsets that v0.4.3 stored. It does
  not invent original provider timestamps, recording timezones, or provider
  reporting periods. The default calendar timezone stays unset unless the athlete
  supplies one. It is never inferred from the data or importing computer. Calendar
  commands refuse rather than guess when no timezone is supplied.
- **Links and conflicts.** Old links used a source plus start time or a benchmark
  plus result time. Migration replaces them with stable record links. No match is an
  error. Several matches are a conflict. Use `ath conflicts show` and
  `ath conflicts resolve`, then confirm the import. A changed package or database
  makes those choices stale and requires a new preview.
- **Predictions.** A prediction's result link, saved grade, and old `miss_analysis`
  become separate records. The new clear name is prediction error analysis. Old
  values are preserved and grades are not recalculated. Old evidence remains a date
  window and text; migration does not invent record citations. A claimed cause that
  matches no old record blocks import. Several matches are kept as possible records
  without claiming which one was used. After migration, explicit grading uses
  prediction and result IDs; the old `ath grade <benchmark> --actual` and
  `ath grade --analysis` forms are removed.
- **Attachments.** Attachments are checked before they are copied. A missing file,
  unsafe file, wrong type, or hash mismatch blocks import.
- **No invented data.** Generic old nutrition reports remain athlete reports.
  Migration does not invent foods, nutrients, plans, goals, or other v1-only records.
- **No inferred deletions.** A missing item in an imported package does not delete a
  local record.
- **Historical queries.** Historical queries use clearly marked time assumptions
  because v0.4.3 did not record when each item first entered the file.
- **Database ID.** A v0.4.3 file has no database ID. The migrated data keeps the ID
  created by `ath init`.
- **Accepted old format.** This path accepts files that pass the v0.4.3 schema and
  checks. A retired older layout needs its provider export or a separately designed
  upgrader.
- **Side files.** Model preferences, backtest reports, and gateway keys remain
  outside the athlete database. Export omits them unless a report is later saved as
  athlete-owned data.
- **Backups.** Do not copy an open SQLite file in WAL mode. Use `ath export` or
  SQLite's online backup operation.

## Migration transaction

`ath init` creates an empty v1.0.0 database with a new database ID. Importing a
v0.4.3 document then:

1. Runs `validateAthleticStandardFile` with the shipped v0.4.3 schema and semantic
   checks.
2. Reads and verifies every available series sidecar and attachment.
3. Builds the complete import preview only after those checks pass.
4. Resolves old source, benchmark, session, result, and prediction references.
5. Writes every accepted record in one transaction after confirmation.
6. Gives each imported record revision 1.
7. Increments the database revision once for the whole import.

The destination keeps the database ID created by `ath init` because a v0.4.3 file
has no database ID to adopt. A fixed import time may be supplied by tests and
reproducible tooling. Revision knowledge times follow the marked legacy rules below;
they are not all replaced with the import time.

The import command does not modify the original document, `series/`, `attachments/`,
model preference, or backtest reports. The preceding `ath init` may refresh the
installed Skill.

## How to read a destination

Every destination in this appendix is an exact v1 record type, SQLite table, or
SQLite column. Plain-language category names are not destinations.

Every athlete-owned record writes three common rows:

- `records` holds `record_id`, `record_type`, `current_revision`, `first_known_at`,
  and `is_deleted`.
- Its typed table holds the current fields. For example, an athlete report uses
  `athlete_reports`.
- `record_revisions` holds revision 1 in `revision` and the complete logical record
  in `record_json`.

Every imported record also writes
`record_import_keys(record_id, match_key_method, match_key,
input_athleticstandard_version, imported_at)`. `match_key_method` is
`legacy-v0.4-id-v1`. `match_key` is the encoded UUIDv5 name described below.
`input_athleticstandard_version` is copied from the top-level
`athleticstandard_version`. `imported_at` is the migration transaction time.
Child rows such as segments use their named child table and their parent's stable
ID. The field tables below do not repeat these common writes on every line.

For example, one old soreness item writes:

```text
records(record_type = 'athlete_report')
athlete_reports(record_id, report_type, reported_at, rating, rating_scale, body_region, text)
record_revisions(record_id, revision = 1, record_json = complete state)
```

It writes `attachments` only when the old item references one. It never writes a
source foreign key.

## Stable IDs

New v1 records use UUIDv7. Legacy records use UUIDv5 under a fixed Athletic Standard
namespace.

The legacy namespace UUID is `a4f17b95-1205-5b33-b97a-cb95098e9b12`. It is the
UUIDv5 result of the RFC namespace URL and
`https://athleticstandard.ai/namespaces/legacy-v0.4`.

The name begins with the string component
`athleticstandard-legacy-v0.4-id-v1`. Each following component is encoded in order.
A string is `s`, its UTF-8 byte length in ASCII decimal, `:`, then its unchanged
UTF-8 bytes. A nonnegative integer uses `i` followed by the same length form for its
ASCII decimal text. An absent optional value is `n0:`. There are no separators
between encoded components. UUID text used as a component is lowercase. This
encoding distinguishes absent, empty, string, and integer values and does not depend
on JSON key order.

The component lists are:

| Legacy record | UUIDv5 name input |
|---|---|
| Athlete profile | `athlete_profile` |
| Source | `source`, old source ID |
| Source device | `source_device`, source UUID, `name`, `manufacturer`, `model`, `hardware`; add original device position when those fields repeat |
| Point measurement | `point`, type, source UUID, `recorded_at`; add original position when repeated |
| Vendor score | `vendor_score`, metric, source UUID, `recorded_at`; add original position when repeated |
| Legacy sample group | `series_receipt`, quantity, source UUID |
| Measurement sample | `series_sample`, quantity, source UUID, reconstructed instant; add original sample position when repeated |
| Sleep session | `sleep_session`, source UUID, `start`; add original position when repeated |
| Workout session | `workout_session`, source UUID, `start`; add original position when repeated |
| Benchmark definition | `benchmark`, old benchmark ID |
| Benchmark result | `benchmark_result`, benchmark UUID, source UUID, `recorded_at`; add original position when repeated |
| Athlete report | `athlete_report`, type, `reported_at`; a later duplicate adds `note`, then original position if still repeated |
| Prediction | `prediction`, old prediction ID |
| Prediction-result link | `prediction_outcome`, prediction UUID, linked result UUID |
| Attachment | `attachment`, owning record UUID, old filename, expected SHA-256 |
| Grade | `grade`, prediction-result-link UUID, `legacy-v0.4-grade` |
| Prediction error analysis | `miss_analysis`, prediction UUID, `legacy-v0.4-miss-analysis` |

The strings in the UUIDv5 input are fixed ID-method tokens. They keep the earlier
`legacy-v0.4-id-v1` values even where the final v1 record type now has a clearer
name.

Mutable source-device coverage fields `from`, `to`, and `n` are not ID components.
Original position is zero-based in the v0.4.3 array. A measurement sample's position is
its zero-based global index after sorting sidecars by filename day and then walking
each file's parallel sample arrays in order.

The first occurrence of a base reference keeps the base UUID. Each later collision
adds its original position to the UUIDv5 input. This implements the plan's
deterministic-suffix rule. Repeating the same package produces the same IDs.

Migration also stores the encoded UUIDv5 name as a
`record_import_keys` entry with `match_key_method = 'legacy-v0.4-id-v1'`. On another import, the
same key and same complete migrated content is a match. The same key with changed
content is previewed as a correction and creates a revision only after confirmation.

Ordered segments, point-measurement calculation details, prediction evidence details,
and other child rows are part of their parent record state. They use the parent ID and their
zero-based order. They do not receive independent legacy UUIDs. Correcting one
creates a revision of the parent and replaces its child rows in the same transaction.

point measurements, sleep sessions, workout sessions, benchmark results,
`series_ref`, and `vendor_score`. Its array index is used for diagnostics and only

## Preserved input times and values

v0.4.3 stores normalized ISO timestamps, not the exact vendor timestamp text that
preceded parsing. Migration preserves the v0.4.3 timestamp and its printed numeric
offset in the exact typed-table columns below. It marks their meaning
`legacy_normalized_timestamp`. Migration does not call the offset a recording
timezone. No IANA timezone is inferred.

Original provider units and values were generally discarded after conversion in
v0.4.3. The standard value and unit are preserved. Their original-source fields
use the missing reason `legacy_not_stored`.

Every migrated measured record sets `received_at` to the v1 migration transaction
time and `received_at_basis` to `legacy_migration_time`. This is when v1 received
the record, not when the old importer first saw the provider row.

The exact columns are `point_measurements.received_at` and
`point_measurements.received_at_basis`, `measurement_samples.received_at` and
`measurement_samples.received_at_basis`, `legacy_sample_groups.received_at` and
`legacy_sample_groups.received_at_basis`, `sleep_sessions.received_at` and
`sleep_sessions.received_at_basis`, `workout_sessions.received_at` and
`workout_sessions.received_at_basis`, `benchmark_results.received_at` and
`benchmark_results.received_at_basis`, and `provider_scores.received_at` and
`provider_scores.received_at_basis`.

The parent `records.first_known_at` copies the same instant as revision 1
`record_revisions.became_known_at`, listed below. Its basis lives in
`record_revisions.became_known_at_basis`; `records` does not duplicate that basis.
Predictions keep their old authored `created_at`. The actual v1 import time is stored
in `record_import_keys.imported_at`. No unmarked record-creation time is invented.

The exact input-time columns are:

| `records.record_type` | Input-time columns |
|---|---|
| `point_measurement` | `point_measurements.input_timestamp_text`, `point_measurements.input_utc_offset_text`, `point_measurements.input_timestamp_basis` |
| `sleep_session` | `sleep_sessions.input_start_timestamp_text`, `sleep_sessions.input_start_utc_offset_text`, `sleep_sessions.input_start_timestamp_basis`, `sleep_sessions.input_end_timestamp_text`, `sleep_sessions.input_end_utc_offset_text`, `sleep_sessions.input_end_timestamp_basis` |

The old calculation details name a quantity and coverage, not exact sample IDs.
Migration keeps that limitation in
`point_measurement_calculations.sample_evidence_status = 'legacy_group_only'`; it
does not invent evidence references. It must resolve a legacy sample group with the
same source and quantity whose declared
coverage includes the derived measurement's date. When matching sidecar samples are
present, it also sets `point_measurement_calculations.legacy_sample_group_id` to
that verified group. It still does not claim which discarded samples were used. A
missing `series/` directory leaves that link pointed at the unavailable group. A
missing matching group is an import error.

### Sidecar files

The expected filename is

sidecar day. Files are selected by the exact quantity and source suffix, as v0.4.3
did, because quantity underscores and source hyphens make delimiter splitting

any database write.

| sidecar field | v1.0.0 destination | Rule |
|---|---|---|

`measurement_samples.record_id`, `measurement_samples.legacy_sample_group_id`, and

source and quantity. Each sidecar writes one ordered child row in
`legacy_sample_files` with `legacy_sample_group_id`, `ordinal`, `relative_path`,
`input_athleticstandard_version`, `start_timestamp_text`, and `file_sha256`. Each
sample also sets `measurement_samples.legacy_sample_file_ordinal` to that child
row's ordinal.

| Sidecar child value | `legacy_sample_files` destination | Rule |
|---|---|---|
| parent sample-group UUID | `legacy_sample_files.legacy_sample_group_id` | Link the `legacy_sample_groups` record for the same source and quantity. |
| filename-day order | `legacy_sample_files.ordinal` | Number from zero after sorting by filename day. |
| selected sidecar filename | `legacy_sample_files.relative_path` | Preserve the validated path relative to the package root. |
| `athleticstandard_version` | `legacy_sample_files.input_athleticstandard_version` | Preserve the sidecar's version. |
| `start` | `legacy_sample_files.start_timestamp_text` | Preserve the complete string verbatim, including its printed offset. |
| exact file bytes | `legacy_sample_files.file_sha256` | Store the verified lowercase SHA-256. |

Sidecar `quantity` and `unit` are not copied onto
`legacy_sample_files`. They are already preserved on the parent
`legacy_sample_groups.quantity`, `legacy_sample_groups.standard_unit`, and every linked
sample.

Samples keep sidecar file order as their original position for collision handling.
The importer also verifies that offsets are nondecreasing, the filename day equals
the first ten characters of `start`, and sidecar quantity, canonical unit, and
source match the group.

The importer hashes each sidecar's exact bytes with SHA-256. It then rebuilds the
v0.4.3 group hash by adding
`<day>:<sidecar-sha256>\n` in filename-day order. That result must equal the
`series_ref.sha256`. It also verifies declared sample count, `from` and `to` against
the first and last filename dates, and `days` against the number of sidecars.
Samples are inserted in bounded prepared batches.

The quantity, source, unit, filename-day, offset-order, count, and coverage checks are
new migration integrity checks. v0.4.3 `ath check` rebuilt only the group hash after
schema validation. Migration makes these relationships explicit before moving the
samples into database rows.

The old sidecar did not keep each vendor timestamp text, original unit, or original
value. Each sample records the missing reason `legacy_sidecar_not_stored`. Its
timestamp calculation keeps the sidecar start and offset. The exact columns are
`measurement_samples.original_timestamp_missing_reason`,
`measurement_samples.original_unit_missing_reason`, and
`measurement_samples.original_value_missing_reason`.

If the `series/` folder is absent, import writes one unavailable legacy series
group per source and quantity with the declared coverage and hash. It writes no
samples. `ath check` reports the missing sample data.

A present sidecar with a hash mismatch is not treated as absent. Import refuses
because the bytes disagree with the document's receipt.

If the `series/` folder exists but any declared sidecar is missing, malformed, or
fails the quantity, source, unit, count, coverage, or hash checks, import refuses and
writes no `legacy_sample_groups` or samples. It does not use a third status value
for a partly present group.

### Inline and series copies

D43 moved dense quantities out of `hard_signals`. A legacy file may still contain an
inline point with the same quantity and source as a `series_ref`.

When verified sidecars are available, migration applies the v0.4.3 D43 rule: no
inline point with that quantity and source becomes a current point record. An exact
quantity, source, instant, value, and unit match is shown as an old duplicate in the
import preview. A nonmatching inline point is unrepresentable and blocks import.
It is neither silently dropped nor counted beside the dense series.

When the series folder is absent, inline points remain point records and the
unavailable legacy sample group remains. No sample is invented from an inline
summary.

A document that claims v0.4.3 but carries retired per-day `series_ref` fields such
as `file`, `summary`, `start`, or `end` fails v0.4.3 validation. This appendix does
not guess how to upgrade a pre-D40 layout. The user must import the original provider
export or use a separately specified older-format upgrader.

## Links

Before resolving links, migration checks for duplicate workout keys
`(source,start)` and duplicate result keys `(benchmark,recorded_at)`. General v0.4.3
validation collapsed those keys into a set or map and did not report duplicates.
Migration reports them as conflicts because a compound link cannot identify one
target.

### Result to workout session

The old `(source,start)` link resolves after all workout sessions have IDs.

- One exact match: write `benchmark_results.workout_session_id` and
  `benchmark_results.workout_session_revision = 1`.
- No exact match: import error.
- Several exact matches: conflict; do not choose by array order.

### Prediction to result

The old `(benchmark,actual.recorded_at)` reference resolves after all results have
IDs, using the rules above.

### Planned-session links

v0.4.3 has no training plans or planned sessions. Migration creates none.

## Revisions and deletion records

v0.4.3 has no revision or deletion records.

- Every imported current record begins at revision 1.
- Every revision stores the complete migrated logical record.
- `record_revisions.previous_revision` is null.
- `record_revisions.author_type` is `tool`.
- `record_revisions.author_tool` is `ath`.
- `record_revisions.author_tool_version` names the migration tool version.
- No `record_deletions` rows are created from absence in the old arrays.

## Provider reporting periods and local dates

The old logical document did not distinguish provider reporting periods from
calendar dates. Migration preserves only what the document proves:

- Existing timestamp strings remain preserved input text.
- Existing `SeriesRef.from` and `to` remain legacy coverage dates.
- Existing device `from` and `to` remain legacy device-window dates.
- No WHOOP cycle, Oura reporting-period type, Apple activity-summary date, recording timezone, or
  travel history is inferred from a generic old timestamp.

Re-importing the original provider export under v1 may produce richer provider
reporting periods. That is a separate provider import preview. It is not silently
folded into the migrated legacy record when the old file lacks a stable provider ID.

| `backtest-*.json` | Leave unchanged. It is not athlete data unless later saved as a review. |

| Installed Skill folders | `ath init` installs the v1 Skill through the normal current-version rule. Old copies are not imported as athlete data. |

## Preview counts

Before confirmation, migration reports:

- Sources and devices.
- Current records by type.
- Legacy sample groups, available sidecars, accepted samples, and missing sample
  groups.
- Attachments copied, missing, rejected, or hash-mismatched.
- Links resolved, missing, or conflicting.
- Legacy fields preserved with explicit missing-detail reasons.
- Unknown or unrepresentable records.

Any error, conflict, unknown field, missing required attachment, or unrepresentable
record prevents the transaction. A missing series folder is the one allowed partial
case because v0.4.3 explicitly permitted a document to travel without its series
sidecars. The unavailable legacy sample group makes that loss visible.

## Required migration fixtures

Migration tests include:

- Every point type, session aggregate, benchmark score type, and soft-signal field.
- Available series with millisecond offsets and durations.
- A missing series folder and its unavailable sample groups.
- D43 inline points that both do and do not exactly match a sidecar sample.
- Vendor scores, point-measurement calculation details, and source-device windows.
- Result-to-session and prediction-to-result links.
- Attachments, including photo provenance and failed hash checks.
- Grades and prediction error analyses with measured and athlete-report causes.
- An `actual` without a grade.
- A legacy `miss_analysis` selector with several possible evidence records.
- Duplicate old references and repeat imports.
- A legacy Oura midnight UTC anchor.

## Round-trip acceptance

The migration is accepted only when:

1. Every v0.4.3 field above is present in the v1 logical export or in named legacy
   metadata.
2. Every available measurement sample survives with its value, duration, quantity,
   source, and reconstructed instant.
3. Every old link resolves to stable record IDs without guessing.
4. The two-tier wall still holds.
5. Exporting and importing the migrated database produces equal logical records,
   revisions, deletion records, legacy sample groups, provider reporting periods,
   and attachment hashes.
6. Repeating the v0.4.3 import produces no records or revisions.

## D101 outcome

D101 rejects this migration design because no real athlete records depend on the
prerelease 0.x format. The v1 CLI refuses Athletic Standard files below version
`1.0.0`. The active v1 schema does not include the legacy-only records, fields, IDs,
time assumptions, or conflict rules described in this appendix.

This appendix is not a schema, implementation requirement, test requirement, or
release gate.
